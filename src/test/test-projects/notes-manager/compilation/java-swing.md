# Java Swing Compilation Guidance

---

## Java Baseline

- Java 17
- UTF-8 source encoding
- Standard Java SE APIs
- User interface interactions occur via Java Swing/AWT standard libraries (`javax.swing.*`, `java.awt.*`) and do not require external UI libraries

---

## Components

- Mutable non-static state only
- Separate UI input/output and business logic

---

## Application

- Started by its `public void static main(String[] args)` method
- UI updates and constructions must occur on the AWT Event Dispatch Thread (EDT) using `javax.swing.SwingUtilities.invokeLater`.

## Java Source

- The directory hierarchy of java source files should be based at the root of the target base. eg: the nl.com.notesmanager.Class will be outputed to the file target:/nl/com/notesmanager/Class. This rule is applied to every java source file generated.
- Java code must be generated exclusively.
- Java code must be generated solely from the main source document. No element that is mentioned by a referenced file should be generated.
- The package for the Java code being generated must be determined from the path of the main source, relative to the base of origin.
- Files generated by referenced files must be retrieved from the hierarchical structure of the provided references tree. Files not present in the references tree must not be sought.
- Files generated by the referenced files in their own reasoning cycle must be inspected to obtain information on dependencies of the code to be generated, such as classes, methods, fields, and properties.
- Previously generated files from the main and referenced sources are listed and attached in previous messages. If a file is tagged with (no generated files), it indicates that no files have been generated by it yet.
- All files required to complete this task are listed and attached to this conversation in previous messages.
- Absolute package names must always be used in import statements. The path of referenced files relative to the base must be used when inferring package names.
- For every generated .java file, compile.sh <path-to-generated-java-file> must be run from the project root using the run_script mcp operation.
- The compiler output for the file must be analyzed to identify all reported errors and warnings.
- All reported compilation errors in the generated file or in directly related generated dependencies must be fixed.
- After each fix, compile.sh must be run again using the run_script operation for the same file, repeating until the command succeeds (up to a limit of 3 attempts). If a clean compilation is not achieved, processing must stop and the user must be informed.
- Only files directly generated from the main source of each inference cycle must be compiled. Files generated from referenced files are compiled in their own inference cycles.
- Only the files already provided must be utilized. Exploratory requests must be avoided.

## Java Compilation Error

- Inference notes must be added to .java files using the add_inference_note operation when compilation errors that should be fixed are found in .java files out of the scope of the current source .md file.
- Inference notes must be added to address every .java file that should be fixed.
- Processing must be finalized (finish_error) with an error message (message-to-user) after addressing every compilation error to be fixed in .java files out of the scope of the current source .md file.

## Need to Change Java Source

- Inference notes must be added to .java files using the add_inference_note operation when a change is needed in files that were not generated by the current main .md source being processed.
- Every .java file requiring changes that was not generated by the current .md source being processed must be addressed before finalizing the pipeline with finish-error and message-to-user.

## Java imports
- Single type imports must be used. Package imports must not be used.
- Fully qualified class names must be used in variable declarations when the code uses classes with the same name to disambiguate the reference.

## Swing GUI Input & Event Handling

- Swing inputs should be gathered via graphical components like JTextField, JTextArea, JComboBox, or JCheckBox.
- GUI actions (button clicks, menu selections, keystrokes) must be handled using Event Listeners (e.g., ActionListener, DocumentListener, ItemListener, or KeyListener).

## Code Completeness

- The most logical and complete behavior must be implemented for the generated code. Empty methods or methods that only return a default value must not be left. The code must be ready to be compiled and run.
- Instructions and design must be followed strictly. No behavior not described in the main source may be inferred or added to the generated code. If the design is unclear or incomplete, clarification must be requested instead of making assumptions.

## JavaDocs

- JavaDocs must be generated for every public class and method. 
- JavaDocs must not be added to private methods, package-private methods, or fields.

## Swing UI

- The Swing UI components must be created, laid out, and updated on the Event Dispatch Thread (EDT) using `javax.swing.SwingUtilities.invokeLater`.
- Visual layout must use standard AWT/Swing layout managers (e.g., BorderLayout, GridLayout, BoxLayout, GridBagLayout, or FlowLayout) to arrange sub-panels, buttons, and input fields.
- Interactive frames (JFrame, JDialog) must set default close operations (e.g., `JFrame.EXIT_ON_CLOSE` or `JFrame.DISPOSE_ON_CLOSE`) and handle layout packing (`pack()`, `setVisible(true)`).

## Corrective notes

- The add_inference_note tool must be used to report issues in files that are out of the scope of the current main source.

## Component naming rules

- The class name specified in the .md file must be used to name the generated Java class.
